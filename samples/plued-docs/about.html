PLUed Help - write-up

How I built PLUed Help

PLUed is an app I built that teaches grocery cashiers the PLU codes they type at the register. Its help started as two long Markdown files. For this sample I rebuilt it as structured DITA 1.3: short topics, one source, and separate help for each audience.

The brief

  • Audiences. Cashiers and shoppers use the app. Store managers and trainers prepare a store's own codes. Each group gets help that holds only what it needs.
  • Task first. Most topics are tasks: what to do, one action per step, what you see after, and a decision table where the path splits.
  • House style. Plain, short sentences in US English, no marketing words, notes only where they earn their place, and the app's exact labels.
  • True to the product. Every statement had to match what the app does today.
  • Look. A help-site layout like the ones AEM Guides publishes: a contents tree, breadcrumbs, search and an "On this page" list, without anyone's branding.

How the work was done

I followed the same process I use for course drafts: I write the brief and the rules, AI produces a first draft, and a person checks it before it goes out.

  • Brief. I set the audiences, the topic list, the style rules and the look.
  • Draft. An AI model (Claude, from Anthropic) read the app and its old help, drafted the topics in DITA, and wrote the build scripts and the toolkit plugin.
  • Review. Every topic was checked against the app's code. I reviewed the published help on a phone and on a wide screen, and directed the changes until it met the brief.

The structure

Every topic is its own file. A root map pulls in one submap per guide, so each guide can be maintained on its own.

PartTopics
Overview3 concepts: what PLUed is, how PLU codes work, who uses the app
User Guide15 topics: 9 tasks, 2 concepts, 4 references
Admin Guide8 topics: 5 tasks, 2 concepts, 1 reference
Glossary11 glossary entries

The same source also holds a Developer Guide for building and releasing the app. It is left out of this sample.

Keys: write a label once

The product name, the version and every on-screen label are keys in the root map. A topic points at the key, so when a label changes in the app, one line changes here.

<!-- plued.ditamap -->
<keydef keys="ui-library"><topicmeta><keywords>
  <keyword>Library</keyword>
</keywords></topicmeta></keydef>

<!-- in a topic -->
<cmd>At the bottom of the screen, tap <uicontrol keyref="ui-library"/>.</cmd>

Reuse: write a step or note once

Steps and notes that several topics need live in one shared topic and are pulled in by reference.

<!-- reuse/shared.dita -->
<note id="note-organic" type="note">For the organic version of any code, add a 9 in front
  of it. For example, 4011 becomes 94011.</note>

<!-- in "How PLU codes work" and "Look up a PLU code" -->
<note conkeyref="shared/note-organic"/>

Decisions as tables

Where the path splits, the step holds a decision table with one row per case.

<step>
  <cmd>Decide how you received the pack.</cmd>
  <choicetable>
    <chhead><choptionhd>If</choptionhd><chdeschd>Then</chdeschd></chhead>
    <chrow>
      <choption>A QR code</choption>
      <chdesc>Tap <uicontrol>Scan QR</uicontrol> and point the camera at the QR code.
        The import starts when the code is read. Continue with step 5.</chdesc>
    </chrow>
    <!-- one row each for a link and a .plupack file -->
  </choicetable>
</step>

Audience filtering

Admin topics are marked audience="admin". A DITAVAL file decides what each build includes, so the user help and the admin help come from the same files.

<!-- ditaval/admin.ditaval -->
<val>
  <prop att="audience" val="user" action="include"/>
  <prop att="audience" val="admin" action="include"/>
  <prop att="audience" val="developer" action="exclude"/>
</val>

Filtering also works inside a topic. The "About PLUed" page lists only the guides that are in the help you are reading.

Related links from one table

Links between topics are not typed into the text. A relationship table in the root map links each concept to the tasks and references that go with it, and a filtered build drops the links to topics it leaves out.

Publishing

  • The DITA Open Toolkit 4.4.1 publishes both help sites as HTML5, with the full table of contents on every page.
  • A small toolkit plugin replaces the page frame with the top bar, the three-column layout and the topic type label. A stylesheet and one script add the collapsible contents, breadcrumbs, search, "On this page", and previous and next links.
  • Each help site opens on a Contents page that lists every topic with its short description.
  • The pages fill the screen they are on, from a phone to a wide monitor.

How it was checked

  • Every file validates against the DITA 1.3 DTDs.
  • Every build completes with no toolkit warnings or messages, including the key and reference checks.
  • Every statement was checked against the app's code.
  • Every link resolves, and every page fits the screen at widths from 360 to 2560 pixels.
